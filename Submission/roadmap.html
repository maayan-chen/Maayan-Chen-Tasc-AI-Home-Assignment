What happens when a folder gets ingested

A consultant types a folder path and a customer name, clicks one button. Everything from here is deterministic Python — reading files, deciding what's new, and saving to the database — except one narrowly-scoped translation step.

For developers — order matters here

The hash/skip check runs before translation, and the xlsx-vs-everything-else chunking split happens after translation — both intentional, not simplified for the diagram. A changed file's old chunks are deleted only after its replacement chunks are saved successfully, so a failed save (e.g. an OpenAI rate limit) never loses a file's content.

For developers — the relevance gate and history fold-in

Chat history isn't rewritten by an LLM into a standalone query — the last HISTORY_TURNS (2) exchanges are just concatenated onto the question text before both the search and the prompt. It's one sentence to explain and needs no extra model call, at the cost of degrading on longer, topic-drifting conversations.

min_relevance (0.7) gates whether an answer is attempted at all — below it, the system says it doesn't know instead of asking gpt-4o to work with weak context.

Why it's built this way

Decisions that will surprise you

Decision 1

Only two LLM calls exist in the whole system

Translating a non-Hebrew document at ingestion, and generating the final answer at query time. Which chunks get retrieved, chunking strategy, dedup, and chat-history handling are all deterministic.

Decision 2

Spreadsheets are chunked row-by-row, not by character count

A real bug: a 300-character chunk boundary could slice a value away from the header row naming its column — a salary number with no way to tell what it was.

Decision 3

One metadata field is the entire trust boundary

context_tag is the only thing that keeps customers' data apart — no separate tables, no separate collections.

For developers — the full reasoning

Each of these is written up with the rejected alternatives and the evidence behind the call in docs/ARCHITECTURE.md — including why a web-search agent was designed and then cut before implementation once it reduced to one fixed, non-judgmental tool call with nothing an agent was actually adding over a consultant Googling the company themselves.

For developers — what actually enforces this

Every similarity search passes filter={"context_tag": context_tag} to pgvector — the active customer selected in the UI is the only value that ever reaches that filter. There's no separate table or collection per customer; isolation is logical, enforced by this one indexed JSONB field on every chunk.

Stated plainly

Limitations

Two known gaps, not hidden and not apologized for — both deliberate trade-offs given the scope.

English questions are sometimes answered in Hebrew

Translating non-Hebrew documents to Hebrew at ingestion closes a real retrieval gap, but it also means most of the store is now Hebrew text — which can outweigh the prompt's instruction to answer in the question's own language. Confirmed as a genuine model-following limit, not a wording problem, and accepted because real usage is expected to be Hebrew-majority.

No per-customer access control

context_tag prevents customer data from being mixed together, but it does not prevent a consultant with access to the app from querying any customer that's been ingested. A real deployment would need authentication and authorization so a consultant only reaches the customers they're actually assigned to.
